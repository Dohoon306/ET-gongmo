> v0.3 (2026-11-20) 팀을 풀스택 4명으로 바꾸고 담당 D를 추가했습니다. 관심 공고 저장(D-1·D-2), 마감일 D-Day 표시(X-6), 익명 평가(A-5·A-6)를 넣었습니다. AI 호출 모듈(X-3)은 B에서 D로 옮겼습니다.
> v0.2 (2026-11-20) 검증 결과 반영. 가입 기능, 방 상태와 규칙, 정렬 기준, 완료 기준, 공통 기능 담당, 화면 목록을 추가하고 추천 쿼리를 고쳤습니다.

### 헤더 메뉴

헤더(A)는 아래 경로로 링크만 겁니다. 가입 화면(1-1, 1-2)에서는 메뉴를 숨기고 로고와 사용자 전환만 보여 줍니다.

| 메뉴 | 경로 | 담당 | 비고 |
|---|---|---|---|
| 추천 공모전 | `/contests` | B | 공모전 상세, 방 목록, 참가 요청에서도 이 메뉴가 켜져 있습니다 |
| 관심 공고 | `/bookmarks` | D | |
| 내 팀 | `/my/team` | C | 현재 사용자가 참여한 공모전 목록(C-7)을 보여 줍니다. 팀을 누르면 팀원 목록(`/rooms/:roomId/members`)으로 갑니다 |
| 받은 요청 | `/my/requests` | C | 현재 사용자가 방장인 방의 받은 요청(`/rooms/:roomId/requests`)으로 보냅니다 |
| 프로필 | `/users/{현재 사용자 ID}` | D | 팀원 평가(6-1)에서도 이 메뉴가 켜져 있습니다 |

- `/my/team`과 `/my/requests`는 C가 만듭니다. 헤더는 방 ID를 몰라도 됩니다 ([DB 명세서 5.7](db-spec.md#57-내-방-찾기-c)).
- 한 사람이 2개 이상의 팀(공모전)에 참여할 수 있으므로 `/my/team`은 참여한 팀을 모두 보여 줍니다 (C-7). 종료된 팀은 빼고, 가장 최근에 들어간 팀이 위에 옵니다.
- `/my/requests`는 현재 사용자가 방장인 방 중 가장 최근에 들어간 방의 받은 요청으로 보냅니다.
- 속한 방이 없으면 "아직 속한 팀이 없어요" 안내와 추천 공모전으로 가는 버튼을 보여 줍니다.
- "받은 요청" 옆 대기 요청 수 배지는 P1입니다. 시안에는 그려 두었습니다.
- 현재 사용자가 비어 있으면 사용자 전환 버튼에 "사용자 선택"을 보여 줍니다.

## 담당 사이 접점

담당끼리는 **코드가 아니라 테이블·고정 ID·화면 경로·스텁**으로만 만납니다. 다른 담당 패키지의 클래스를 import하지 않고, 다른 담당 테이블은 native SQL로 읽기만 합니다. 읽는 관계는 [DB 명세서 1장](db-spec.md#1-한눈에-보기)에 있습니다.

| 담당 | 맡는 테이블 | 시드 조각 | 백엔드 패키지 | 화면 폴더 |
|---|---|---|---|---|
| A | `category`, `users`, `user_category` | 카테고리, 사용자 1~7 | `user`, `common` | `features/user` |
| B | `contest`, `contest_category` | 공모전 스냅샷 | `contest` | `features/contest` |
| C | `room`, `room_category`, `room_member`, `join_request` | 방 1~5, 팀원 | `team` | `features/team` |
| D | `bookmark`, `evaluation` | 평가 1건 | `bookmark`, `profile` | `features/bookmark`, `features/profile` |

**첫날 계약.** 각자 다른 파일이라 병렬로 올리고, 약 1시간이면 끝납니다. 이게 올라오면 서로를 기다리지 않고 개발합니다.

| 담당 | 첫날에 올릴 것 |
|---|---|
| A | 자기 DDL(`user.sql`), `AiClient.ask(prompt, fallback)`과 `fallback`만 돌려주는 기본 구현, `GET /api/users` |
| B | 자기 DDL(`contest.sql`), 같은 형식의 개발용 샘플 스냅샷(주인공 공모전 포함. 수집 결과가 나오면 교체), 주인공 공모전 `gongmoa_id` 상수 |
| C | 자기 DDL(`team.sql`), `/my/team`·`/my/requests` 경로 (자리만 먼저) |
| D | 자기 DDL(`bookmark.sql`, `profile.sql`), `SeedContributor` 인터페이스와 `seed` 러너, `DDayBadge`·`BookmarkButton` 스텁 |

**고정 값.** 시드가 서로의 ID를 직접 쓰므로 바꾸지 않습니다.

- 카테고리 ID: [DB 명세서 6.1](db-spec.md#61-카테고리-시드) 순서대로 1부터
- 사용자 ID: 1~7 (시연 중 가입한 새싹은 8)
- 방 ID: 1~5 (방 5가 끝난 팀)
- 시드 순서: A(카테고리, 사용자) → B(공모전) → C(방) → D(평가)

**화면 이동 경로.** 다른 담당 화면으로 가는 링크는 아래 경로만 씁니다.

| 어디서 | 어디로 | 경로 |
|---|---|---|
| 헤더 메뉴 (A) | 각 담당의 첫 화면 | [헤더 메뉴](#헤더-메뉴) 표의 경로 |
| 관심 공고 목록(D-2) 카드 | 공모전 상세(B-4) | `/contests/:contestId` |
| 관심 공고 목록(D-2) 빈 상태 버튼 | 추천 공모전(B-3) | `/contests` |
| 모집 방 목록(C-2) 위 공모전 정보 | 공모전 상세(B-4) | `/contests/:contestId` |
| 공모전 상세(B-4) | 모집 방 목록(C-2) | `/contests/:contestId/rooms` |
| 팀원 목록(C-6) 이름 | 프로필(D-4) | `/users/:userId` |
| 프로필(D-4) 함께한 팀 | 팀원 평가(D-3) | `/rooms/:roomId/review` |
| 추천 공모전(B-3)·상세(B-4)의 저장 버튼 | 관심 공고 저장·해제(D-1) | `BookmarkButton`만 가져다 씀. 저장 상태는 D의 ID 목록 API로 표시 |

기능 하나가 다른 담당 화면을 열어야 하면 경로로 링크만 겁니다. 그 화면의 컴포넌트를 가져다 쓰는 것은 `BookmarkButton`과 `DDayBadge`뿐입니다. 시드에 카테고리가 붙은 사용자가 미리 들어 있으므로 A의 가입 화면이 완성되기를 기다릴 필요가 없습니다.

## A. 사용자 판단

| ID | 기능 | 설명 | 우선순위 | 완료 기준 |

## D. 관심 공고 · 팀원 평가

| ID | 기능 | 설명 | 우선순위 | 완료 기준 |

| D-1 | 관심 공고 저장·해제 | 공모전 카드(B-3)와 상세(B-4)의 저장 버튼으로 현재 사용자의 관심 공고에 넣거나 뺍니다. 버튼 컴포넌트(`BookmarkButton`)는 D가 만들고, B는 화면에서 가져다 씁니다 | P0 | 저장하면 버튼이 저장됨 상태로 바뀌고, 다시 누르면 해제된다. 같은 공모전을 두 번 저장해도 한 번만 남는다. 다른 사용자로 바꾸면 그 사용자의 저장 상태가 보인다 |
| D-2 | 관심 공고 목록 | 현재 사용자가 저장한 공모전을 마감 임박순으로 보여 주고, 마감일을 D-Day 배지(X-6)로 표시합니다. 마감이 지난 공고는 지우지 않고 "마감된 공고" 구분 아래 맨 아래에 흐리게 보여 줍니다 | P0 | D-1에서 저장한 공모전이 바로 목록에 보이고, 누르면 상세(B-4)로 간다. 목록에서 바로 해제할 수 있다. 저장한 공고가 없으면 추천 공모전(B-3)으로 가는 안내가 보인다 |
| D-3 | 팀원 평가 | 종료된 팀에서 다른 팀원에게 별점(1~5)과 한 줄 코멘트를 **익명으로** 남깁니다 (평가 항목은 회의에서 확정, 지금은 가정). 평가 화면에는 "평가는 익명으로 남아요" 안내를 보여 줍니다. 이미 평가한 팀원의 카드에는 "평가 완료" 옆에 "수정" 버튼을 표시합니다 | P0 | 종료된 팀의 팀원은 같은 팀의 다른 팀원별로 평가 한 건을 남길 수 있다. "수정"을 누르면 기존 별점과 코멘트가 채워진 평가 폼이 열린다. 저장하면 기존 평가가 갱신되고 상대 프로필(D-4)에 수정된 코멘트와 다시 계산된 평균 별점이 반영되며, 평가 수는 그대로다. 취소하면 기존 평가가 유지된다 ([익명 평가 규칙](#익명-평가-규칙)) |

- 저장 상태는 B의 추천 쿼리(B-3)를 고치지 않고, 프론트가 D의 "내가 저장한 공모전 ID 목록" API를 따로 불러 버튼에 표시합니다. B와 D가 같은 쿼리를 건드리지 않기 위해서입니다.
- 테이블은 [DB 명세서 3.11 `bookmark`](db-spec.md#311-bookmark--관심-공고-d-d-1)에 있습니다.
- 평가·프로필은 C의 `room`·`room_member`와 A의 `users`·`user_category`를 native SQL로 읽기만 합니다. 개발은 시드의 방 5(종료된 팀)로 합니다.

### D-3 평가 수정

- "평가 완료" 표시 바로 옆에 "수정" 버튼을 둡니다. 누르면 기존 별점과 코멘트를 채운 평가 폼을 열고 "저장"과 "취소"를 보여 줍니다.
- 서버는 작성과 수정 모두에서 팀이 종료됐는지, 현재 사용자(`X-User-Id`)와 평가 대상이 같은 팀의 서로 다른 팀원인지 확인합니다. 수정할 때는 팀·현재 사용자·평가 대상으로 기존 평가 한 건을 찾아 별점(1~5)과 코멘트(최대 200자)를 갱신합니다. 평가 삭제는 지원하지 않습니다.
- 저장에 성공하면 폼을 닫고 "평가 완료"와 "수정"을 다시 보여 줍니다. 저장에 실패하면 입력값을 유지하고 오류를 표시해 다시 시도할 수 있게 합니다.

## 방 상태와 규칙

```
모집 중 ──(팀원 수 = 정원, C-5)──▶ 모집 완료 ──(이번 범위에서는 시드로만)──▶ 종료
```

| 규칙 | 내용 |
|---|---|
| 정원 | **방장을 포함한** 인원입니다. 방1은 정원 3명에 지금 2명(방장 김, 팀원 정)입니다 |
| 모집 완료 | 팀원 수가 정원에 닿으면 자동으로 바뀝니다. 남은 대기 요청은 거절되고, 방 목록 맨 아래로 내려갑니다 |
| 종료 | 공모전이 끝난 팀입니다. 이번 해커톤에서는 종료로 바꾸는 화면 기능을 만들지 않고, 시드로만 만듭니다 (장면 6) |
| 평가 | 종료된 팀에서만 할 수 있습니다 (D-3) |
| 공모전 연결 | 방은 공모전 1개에 연결됩니다 (1:1 가정, 회의에서 확정). 종료된 팀은 공모전 연결을 비워 둘 수 있습니다. 지난 공모전은 공모아뷰에서 받을 수 없기 때문입니다 |
| 방 목록 노출 | 모집 중 → 모집 완료 순서로 보이고, 종료된 팀은 방 목록에 나오지 않습니다 |
| 여러 팀 참여 | 한 사람은 2개 이상의 팀(서로 다른 공모전의 방)에 동시에 속할 수 있습니다. 같은 방에는 한 번만 들어갑니다 (C-4, `room_member` UNIQUE). 참여한 팀은 "내 팀"(C-7)에서 모아 봅니다 |

## 마감일 표시

공모전 마감일(`contest.end_date`)을 오늘(한국 날짜) 기준 남은 날수로 보여 줍니다 (X-6).

| 남은 날수 (마감일 − 오늘) | 표시 | 예 (오늘 2026-11-20) |
|---|---|---|
| 1일 이상 | `D-{남은 날수}` | 마감 2026-11-22 → `D-2` |
| 0일 | `D-Day` | 마감 2026-11-20 → `D-Day` |
| 음수 | `마감` | 마감 2026-11-19 → `마감` |
| 마감일 없음 | `상시` | `end_date`가 비어 있음 |

- 배지 옆에 마감 날짜도 같이 보여 줍니다 (예: `D-2 · 11.22 마감`). 마감이 지난 공고는 "마감"이 두 번 나오지 않게 `마감 · 11.19 종료`로 적습니다. `상시`에는 날짜를 붙이지 않습니다.
- `D-3`부터 `D-Day`까지는 강조 색(`accent/soft` 바탕에 `accent/default` 글자)으로 보여 줍니다. 그 밖은 [디자인 토큰](#디자인-토큰)의 회색 바탕입니다.
- 날짜만 비교합니다. 시각은 보지 않으므로 마감 당일에는 하루 종일 `D-Day`입니다.
- 추천(B-3)에는 마감이 지난 공모전이 나오지 않으므로 `마감` 배지는 관심 공고 목록(D-2)에서만 보입니다.

| 평가한 사람 본인 | 평가 화면(D-3)의 "수정" 폼에는 현재 사용자가 해당 팀원에게 작성한 별점과 코멘트만 채웁니다. 기존 평가를 불러오거나 저장할 때 서버에서 작성자 본인인지 확인합니다 |
| 추측 막기 | 팀이 2~4명이라 코멘트에 팀 이름이나 날짜가 붙으면 누가 썼는지 짐작할 수 있습니다. 코멘트 목록에는 별점과 내용만 보여 주고, 팀 이름·날짜는 붙이지 않습니다 |
| 순서 | 작성한 순서대로 보여 주면 마지막에 평가한 사람을 짐작할 수 있습니다. 별점 높은 순, 같으면 내용 가나다순으로 정렬합니다 |

AI는 이 목록 **밖의 태그를 만들지 않습니다.** 겹침 계산이 이 목록의 ID 기준이기 때문입니다.

## 외부 API: 공모아뷰

> 2026-11-20에 직접 호출해 확인한 내용입니다. 안내 페이지: https://www.gongmoaview.com/about/open-data

공모아뷰는 REST API가 아니라 **MCP 서버**와 **RSS**를 제공합니다. 둘 다 가입이나 인증 키가 필요 없습니다.

### MCP 서버 (주로 쓸 것)

- 주소: `POST https://www.gongmoaview.com/mcp`
- 형식: JSON-RPC 2.0. 세션을 만들지 않고 `tools/call`을 바로 호출해도 동작합니다.
- 헤더: `Content-Type: application/json`, `Accept: application/json, text/event-stream`
- `User-Agent`도 넣어야 합니다. Python `urllib` 기본값(`Python-urllib/…`)으로 부르면 403이 납니다. 다른 HTTP 클라이언트도 기본 User-Agent를 쓰면 막히는지 확인해야 합니다.

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search_contests",
           "arguments":{"type":"contest","field":["it"],"target":["univ"],"sort":"due","limit":20}}}
```

| 도구 | 입력 | 돌려주는 것 |
|---|---|---|
| `search_contests` | `q` 검색어, `type` (contest/outside/educate), `field[]` 분야 코드, `target[]` (kid/teen/univ/adult/biz), `area[]` 지역, `due` (3/7/30/month), `sort` (due/new/prize/sources), `fresh` (today/yesterday), `limit` (최대 20) | **지금 접수 중인** 공고 목록 |
| `get_contest` | `id` (공고 주소 `/contests/{id}-제목`의 숫자) | 공고 한 건의 상세 정보 |

`search_contests`는 한 번에 최대 20건만 주고 다음 페이지를 받는 인자가 없습니다. 2026-11-20 기준 분야별 접수 중 공고는 37~171건이었으니, 분야마다 정렬 순서(`sort`)대로 앞 20건만 받게 됩니다.

**응답은 JSON 필드가 아니라 마크다운 텍스트**(`result.content[0].text`)라서 서버에서 파싱해야 합니다.

`search_contests` 한 줄 형식:

```
- {제목} — {유형} · {주최} · 마감 {YYYY-MM-DD} · 1등 {상금} · 출처 {N}곳 · {공모아뷰 링크}
```

상금 항목은 없을 수 있으니 앞에서부터 순서대로 자르지 말고, `마감`·`출처`·`https://` 같은 앞머리로 구분합니다.

`get_contest` 형식 (`- 키: 값` 줄 + 원문 링크 목록):

```
# {제목}
- 유형: 공모전
- 주최: 조달청
- 접수 기간: 2026-10-12 ~ 2026-11-22
- 대상: 누구나
- 분야: 게임/소프트웨어 · 문학/수기 · 영상/UCC
- 1등 상금: 200만원
- 공모아뷰 페이지: https://...
## 확인할 수 있는 곳
- 주최 측 원문: https://...
- 링커리어: https://...
```

공고에 따라 `- 주의: 출처마다 접수 기간이 다름 — 원문 확인 필요`, `- 혜택:`, `- 활동 기간:`, `- 장소·방식:`, `- 비용:`, `- 후원:` 줄이 더 붙습니다. 모르는 키는 건너뛰고, `raw_text`에 원본을 남겨 둡니다.

2026-11-20에 실제 공고 90건을 받아 확인한 점 (컬럼별 길이는 [DB 명세서 3.4](db-spec.md#34-contest--공모전-b-b-1)):

- `- 1등 상금:` 줄은 49건에만 있습니다. 상품이 걸린 공고는 `- 1등: 애플 맥북 …`처럼 키가 다릅니다.
- `- 혜택:` 줄은 73건에 있습니다 (예: `상금(총상금 : 650만원 / 1위 : 300만원)`).
- `- 주의:` 줄은 8건에 있습니다. 문구 전체를 비교하지 말고 키가 있는지로 판정합니다.
- 3건은 `주최 측 원문` 링크가 없고 다른 사이트 링크만 있습니다.
- `get_contest`를 1초 간격으로 부르면 90건 중 36건이 502·530 오류로 실패했습니다. 2초 간격으로 다시 부르니 모두 받아졌습니다.

`get_contest`의 분야는 코드가 아니라 원 사이트의 분야 이름입니다. 분야 태그는 **어느 분야 코드로 검색해서 나왔는지**를 기준으로 붙이는 편이 정확합니다.

### RSS (보조)

- 주소: `https://www.gongmoaview.com/rss.xml` (최대 10분마다 갱신)
- 최근 공고와 사이트 게시글(공모 인사이트, 공지사항)이 섞여 약 85건이 옵니다. 링크가 `/contests/`로 시작하는 항목만 공고입니다.
- 분야 정보가 없어서 추천에는 쓰기 어렵습니다. "새 공고 알림" 같은 추후 기능에 쓸 수 있습니다.

### 저장 방식 (결정)

> 2026-11-20 결정: 공모아뷰 데이터는 MySQL에 넣어 두고 진행합니다.

```
수집 스크립트 (수동 실행 또는 하루 1회)
  → 공모아뷰 MCP 호출 (get_contest는 2초 간격, 502·530이면 재시도) → 마크다운 파싱 → MySQL upsert (+ JSON 스냅샷 저장)
시드 스크립트 (복구용)
  → JSON 스냅샷 → 같은 upsert 로직 → MySQL
앱 (추천, 상세, 방 목록)
  → MySQL만 조회
```

이유: 마크다운 파싱을 수집할 때 한 번만 하고, 추천 정렬을 카테고리 JOIN으로 계산하며, 마감돼 공모아뷰에서 사라진 공모전(주인공 공모전 포함)도 남기고, 시연 중 외부 호출과 호출 제한을 피하기 위해서입니다.

테이블 정의(`contest`, `contest_category` 포함), upsert 규칙, 추천 쿼리(B-3)는 [DB 명세서](db-spec.md)에 있습니다.

- upsert는 `INSERT ... ON DUPLICATE KEY UPDATE`로 하고, 마감된 공고는 지우지 않습니다.
- 추천은 겹침 0개인 공모전도 나오도록 `LEFT JOIN`으로 세고, 동점이면 마감 임박순입니다 ([DB 명세서 5.1](db-spec.md#51-공모전-추천-b-3)).

### 이용 규칙

- 화면에 출처 **'공모아뷰'**를 밝히고, **공모아뷰 공고 링크를 그대로** 남깁니다.
- 지원·접수는 주최 측 원문에서 하도록 안내합니다. 공모아뷰는 공고를 주최하거나 접수하지 않습니다.
- 너무 자주 부르면 제한될 수 있습니다 (RSS 기준 10분에 한 번이면 충분하다고 안내). 시연 중에 매번 부르지 말고, **미리 한 번 수집해 DB에 저장**한 뒤 그 데이터를 씁니다. 수집할 때도 `get_contest`는 2초 간격을 둡니다.
- `search_contests`는 접수 중인 공고만 돌려줍니다. 마감된 공모전은 다시 받을 수 없으니 시연에 쓸 공모전은 스냅샷으로 꼭 보관합니다.
